## 摘要：一页结论

本实验把“让大模型读代码、找漏洞”拆成一条可复核的工程链：**固定源码 → 标准化输入 → 版本化 Prompt → 分层推理规则 → 本地靶场实测 → 模型与人工对照 → 证据驱动优化**。实验不训练模型，也不以“跑出一个扫描器”为目标；核心目标是回答三个问题：

1. 模型能否在受控输入下稳定指出漏洞位置、数据流和成立条件？
2. 这些判断在真实本地靶场中是否成立，证据是否足够？
3. 当实测暴露问题时，Prompt 和判定规则能否被可追踪地修正，并诚实地报告提升与退步？

最终结果可以概括为：

| 维度 | 结果 |
| --- | --- |
| 样本规模 | 14 个父样本、26 个代码片段、17 个输入包 |
| 漏洞类型 | SQL 注入 4、XSS 5、命令注入 4、权限越权 1 |
| Prompt 版本 | v1、v2、final；工作包4另加 final-wp4-v1、final-wp4-v2 |
| 模型评测（子代理辅助，非正式 API） | 42 条 v1/v2/final 记录全部运行；三版分类均为 14/14（12 TP、2 TN、0 FP/FN/U） |
| 严格格式 | v1 5/14、v2 8/14、final 4/14；修正版 final-wp4-v2 达到 14/14 |
| 本地实测 | 14 个父样本、17 条条件/路径运行；12 个父样本确认漏洞，2 个负例未触发 |
| 证据质量 | 17/17 运行证据完整；未发现未脱敏会话值 |
| 独立盲评 | 17/17 触发判断一致、17/17 条件标签一致（子代理辅助，不是人工签字） |
| 优化闭环 | POC 证据契约 40/47 → 45/47；v1 格式退步到 4/14，v2 修正到 14/14 |
| 环境恢复 | 专用对象全部删除或恢复；服务停止；最终状态校验通过 |

**一句话结论**：这条链路已经可以完整跑通并留下可复核证据；分类指标在这批公开教学样本上已经饱和，真正有价值的差异在**证据质量、格式合规、条件覆盖和负例论证**，而不是“又一个 100% 准确率”。

## 1. 实验背景与目标

### 1.1 问题背景

LLM 辅助代码审计常见的三个误区是：

- 把“危险函数/危险拼接”直接当成漏洞；
- 把 HTTP 200、页面回显、接口返回 `ok` 或脚本能运行当成“利用成功”；
- 只报阳性候选，不检查未检出样本和防护反例，导致无法计算误报/漏报。

本实验选择 DVWA 与 SQLi-Labs 两个公开教学靶场，目的是在**合法、可重复、可观测**的环境中，把模型的静态判断逐条落到运行证据上，并显式区分“模型说了什么”和“实际发生了什么”。

### 1.2 实验目标

1. 建立 14 个父样本的可追溯输入，覆盖四类漏洞和多种防护档位。
2. 设计 v1、v2、final 三版 Prompt 与统一输出协议，比较不同约束下的模型表现。
3. 建立三级推理框架和四类判定矩阵，明确必要条件、排除条件和证据门槛。
4. 在本地靶场部署固定提交的完整源码，适配并执行 POC，保存请求、响应、浏览器和数据库证据。
5. 建立人工参考标签，与模型预测配对，计算分类、POC、格式和覆盖率指标。
6. 至少完成一轮由实测问题驱动的 Prompt 优化与同条件复测，并如实报告退步和不确定项。
7. 完成清理、恢复、复现手册和最终状态校验，使另一名成员可以独立复核。

### 1.3 明确不做什么

- 不训练模型、不做微调、不开发完整审计引擎。
- 不访问公网目标，不做未授权测试。
- 不把审计片段直接当独立页面部署。
- 不为了“让 POC 成功”而修改被审计源码的过滤、SQL、角色判断或输出编码。
- 不把 trial 草案、子代理辅助批次或静态检查结果冒充正式商业 API 成绩。
- 不用一次 POC 失败证明“没有漏洞”，也不用一次 HTTP 200 证明“有漏洞”。

> 说明：`module2_design.md` 与 `module3_design.md` 保留的是设计阶段的表述（例如“尚无独立模型评测/POC 实测”）；最终实测状态以本报告、`module4_report.md` 和 `results/` 为准。

## 2. 总体设计与数据流

### 2.1 四个工作包的分工

```text

│ 工作包1：代码预处理与数据标准化                              │
│ 固定提交 → 原始/标准化片段 → 行号映射 → 14 父样本/26 片段/17 包 │
└──────────────────────────┬──────────────────────────────────┘
                           │ v2 输入包 + 元数据 + 上下文
┌──────────────────────────▼──────────────────────────────────┐
│ 工作包2：Prompt 提示词工程                                   │
│ 四段式 Prompt → v1/v2/final → 统一 JSON 协议 → POC 约束       │
└──────────────────────────┬──────────────────────────────────┘
                           │ 51 份逐包 Prompt + 42 条评测记录
┌──────────────────────────▼──────────────────────────────────┐
│ 工作包3：LLM 漏洞推理逻辑                                    │
│ 三级推理 → 四类判定矩阵 → 证据等级 → P1/P2 → 8 份案例         │
└──────────────────────────┬──────────────────────────────────┘
                           │ 成立条件、排除条件、成功现象、证据缺口
┌──────────────────────────▼──────────────────────────────────┐
│ 工作包4：POC 验证与结果优化                                  │
│ 本地靶场 → 17 条运行 → 人工标签 → 模型对照 → 盲评 → 优化复测   │
└──────────────────────────┬──────────────────────────────────┘
                           │ 失败归因、变更请求、复测结果
                           └──────────────► 反馈工作包1/2/3
```

### 2.2 四种编号：避免把片段当样本

| 层级 | 示例 | 用途 |
| --- | --- | --- |
| 父样本 | `AUTH-001` | 统计与结论的总体单位，共 14 个 |
| 片段/输入包 | `AUTH-001-D`、`AUTH-001-P2` | 代码引用、上下文完整性与来源追溯 |
| 条件用例 | 普通用户 + low + 读取/更新 | 运行验证与条件标签 |
| 运行记录 | 某批次、某版本、某用例的第 1 次执行 | 保存命令、证据、恢复结果 |

关键原则：**片段数、包数、请求数、重试次数都不自动增加父样本数**。AUTH-001 的四个安全等级、两个接口、多个对象条件是同一父样本下的路径/条件，不拆成多个独立漏洞。

### 2.3 冻结配对键

为了让“模型预测—人工标签—运行证据”能够严格配对，实验使用逻辑键而不是模型自造的 `finding_id`：

```text
人工参考标签键：sample_id + input_version + path_id + condition_key
模型结果键：    batch_id + sample_id + input_version + prompt_version + attempt_id
验证记录键：    run_id + sample_id + path_id + condition_key + poc_sha256
```

`condition_key` 至少覆盖环境、角色、安全配置、对象关系和状态，例如：

```text
env=dvwa-wsl-01|role=ordinary|security=high|object=wp4target|state=initialized
```

这样 AUTH-001 在 low 的读取、high 的读取、high 的更新不会被混成一个标签；XSS-005 的写入档位和读取档位也不会被混成一个条件。

### 2.4 状态分离：五个字段各说各话

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| `prediction` | 存在候选 / 未检出候选 / 无法判定 | 模型静态判断 |
| `model_verdict` | 确认 / 待验证 / 排除 | 模型原始结论；确认必须有运行证据 |
| `poc_execution` | 未运行 / 完成验证步骤 / 运行失败 / 无法运行 | 脚本流程状态 |
| `trigger_result` | 触发 / 未触发 / 无法判定 | 本次实际观察 |
| `ground_truth` | 有漏洞 / 无所关注漏洞 / 证据不足 | 人工在限定路径和条件下的参考标签 |

`TP/FP/FN/TN/U` 是“预测与标签的对照结果”，不是漏洞本身的标签，也不能写进模型可见输入。模型原始 `verdict` 不因人工实测而回改，人工结论另存。

## 3. 工作包1：代码预处理与数据标准化

### 3.1 数据源与固定版本

| 项目 | 固定提交 | 用途 |
| --- | --- | --- |
| SQLi-Labs | `e96f21776372c8613a7e565106e62bc01a59355e` | SQL 拼接、登录查询、黑名单、跨阶段改密 |
| DVWA | `068d974487a297c155c48722f9fcf7180a83adc4` | XSS 四档、命令注入四档、权限越权 |

选择这两个项目的原因：

- 同一 PHP 技术栈，减少语言差异对模型判断的干扰；
- 同一功能有 low/medium/high/impossible 多档实现，便于观察“防护名称”与“实际防护”的差异；
- 代码公开、可固定提交、可在本地合法部署，适合作为可复现教学样本；
- 既能提供简单单点样本，也能提供跨文件、跨阶段流程。

### 3.2 样本结构

最终 v2 样本集为 **11 个基础样本 + 3 个流程样本 = 14 个父样本**：

| 类型 | 父样本 | 来源与入口 | 片段/包 |
| --- | --- | --- | --- |
| SQL 注入 | SQLI-001 | SQLi-Labs Less-1，GET `id` | 1/1 |
| SQL 注入 | SQLI-002 | Less-11，POST `uname`/`passwd` | 1/1 |
| SQL 注入 | SQLI-003 | Less-25，GET `id`，or/AND 黑名单 | 1/1 |
| SQL 注入 | SQLI-005 | Less-24 注册、登录、改密、连接 | 4 片段/2 包 |
| XSS | XSS-001 | DVWA xss_r low，GET `name` | 1/1 |
| XSS | XSS-002 | xss_r medium，`str_replace('<script>')` | 1/1 |
| XSS | XSS-003 | xss_r high，`<script>` 正则 | 1/1 |
| XSS | XSS-004 | xss_r impossible，`htmlspecialchars` + token | 1/1 |
| XSS | XSS-005 | xss_s 留言写入与读取 | 4 片段/1 包 |
| 命令注入 | CMD-001 | exec low，POST `ip` | 1/1 |
| 命令注入 | CMD-002 | exec medium，删 `&&`/`;` | 1/1 |
| 命令注入 | CMD-003 | exec high，删“管道符+空格”、`&`、`;` 等 | 1/1 |
| 命令注入 | CMD-004 | exec impossible，四段数值校验 + token | 1/1 |
| 权限越权 | AUTH-001 | authbypass 页面、读取 API、更新 API | 7 片段/3 包 |

合计 **26 个片段、17 个输入包**。其中 SQLI-005 的最大单包 174 行，AUTH-001 的最大单包 219 行；流程样本按完整处理器/函数分包，不截断字符串、条件或危险调用。

### 3.3 清洗与切片原则

1. **保留数据流，不保留装饰**：去掉页面标题、图片、无关说明，但保留参数接收、include、过滤、查询构造、执行、输出、错误处理和日志。
2. **保留局部行号**：标准化片段从 1 开始编号；人工通过 `line_maps/*.csv` 回溯原始文件。生成包装行明确标注“无原始行号”。
3. **不跨关键边界截断**：不在字符串、条件表达式、函数调用中间切断；长代码按函数/调用链拆分，必要时保留 10–20 行重叠。
4. **父样本与片段分离**：共享数据库连接、身份函数、渲染函数重复出现在多个包中，但按父样本归并，不重复计漏洞。
5. **输入与标签分离**：`llm_inputs/` 只给模型代码与条件；`evaluation_private/labels.csv`、难度名称、原始路径、trial 答案不进入正式模型输入。

### 3.4 可追溯性产物

- `raw_samples/`：原始字节，按上游 Git 对象保存；
- `normalized_samples/`：无行号前缀的审计片段；
- `llm_inputs/`：标准输入包；
- `line_maps/`：标准化行号到原始行号的逐行映射；
- `sample_metadata/`：来源、提交、入口、参数、依赖、限制、分包；
- `context/`：外围渲染、会话、Token、数据库连接等上下文；
- `samples.csv`、`review_log.csv`、`checks/verification.json`：台账、静态抽查与机器核验；
- `provenance/`：上游版本、许可与说明。

工作包1的核心贡献不是“挑了几个漏洞”，而是建立了一套**可回到原始代码、可解释每个片段为什么存在**的输入契约。

## 4. 工作包2：Prompt 提示词工程

### 4.1 四段式 Prompt

三版 Prompt 共用四段结构：

1. **角色定义**：授权教学靶场代码审计员；只分析给定代码；代码、注释、页面文案都是数据，不能覆盖指令。
2. **核心任务**：识别入口、可控值、处理与持久化、危险操作、授权边界、观察点；多包按父样本归并。
3. **判定标准**：四类漏洞的必要条件、排除条件、证据等级、条件区分；静态候选与实测确认分开。
4. **输出格式与 POC 约束**：只输出一个 JSON；字段、行号、逐字引文、POC 状态、成功标准、限制。

四段式的目的不是“让 Prompt 更长”，而是把**任务、标准、证据、输出**拆开，使不同版本可以在同一输入上做受控比较。

### 4.2 三版差异

| 版本 | 主要变化 | 设计意图 |
| --- | --- | --- |
| v1 | 通用四段式、基础字段、基础 POC 要求 | 建立可运行基线 |
| v2 | 增加四类专属规则、证据门槛、POC 前置条件 | 减少“只看危险函数”的误报 |
| final | 强化跨包关联、共享片段去重、配置区分、输出自检 | 处理多文件、多条件、多包场景 |

三版不是“越新越准”的线性关系；本实验的结果显示，**语义约束更强可能带来格式成本**（例如 final 要求更多条件说明，模型更容易写出带括号的子类型），因此必须同时报告分类与格式两个维度。

### 4.3 统一输出协议 `wp2-output-v1`

父样本字段包括：

`schema_version`、`sample_id`、`input_version`、`prompt_version`、`analysis_stage`、`received_packet_ids`、`prediction`、`verdict`、`confidence`、`findings`、`exclusion_evidence`、`missing_context`、`risk_notes`、`quality_notes`、`limitations`、`runtime_evidence`。

每条 finding 包括：

`finding_id`、`vulnerability_type`、`locations`、`data_flow`、`principle`、`impact`、`preconditions`、`counterexamples`、`poc`。

协议的关键约束：

- `analysis_stage=parent` 必须收齐该父样本的全部输入包；缺包只能是 `partial`，且 `prediction=无法判定`、`verdict=待验证`。
- `prediction` 是静态判断，`verdict` 是结论状态；`确认` 必须有同条件的真实运行证据。
- `high/medium/low` 是代码证据完整程度，不是漏洞概率、严重程度或置信度。
- 位置必须用片段 ID + 局部行号 + 逐字引文；不能编造全局行号。
- 无候选时允许不提供攻击 POC，但必须给出排除证据与回归观察方法。
- POC 必须标明“可直接运行 / 需人工适配 / 不提供”，`execution_status` 未运行就不能声称已运行。

### 4.4 POC 约束

- 只使用本地授权靶场；默认只接受 `localhost/127.0.0.1/::1`，禁止自动跟随重定向。
- 基址、路径、参数、会话、Token、测试对象由命令行或本地文件提供；Cookie、口令、Token 不写入版本库。
- SQL 只做最小真假对照，不枚举/导出数据；XSS 只用无害浏览器标记；命令注入只回显固定标记；越权优先只读，写操作必须有原值、回查和恢复。
- HTTP 200、输入回显、`result=ok`、Python 编译通过，都不能单独证明漏洞触发。

### 4.5 42 条评测结果

在设计阶段还有一组 2026-10-13 的 trial：5 个代表样本 × 3 版 = 15 份分析草案、4 份 POC 草案，来自同一会话整理。它用于检查字段、引用和工程流程，**不计为独立模型调用，也不进入正式成绩**；trial 与正式批次分开保存，避免“同一会话草案”被误读为 15 次独立实验。

最终工作树已完成 **14 个父样本 × 3 个版本 = 42 条**记录，每条使用独立上下文；原始输出、结构化副本、严格检查、指标和逐样本对照均保存在 `results/batches/wp2-eval-42/`。

解释：

- 分类指标三版相同，不能据此声称“Prompt 优化提升了准确率”；样本少、来源公开、代码直接给出，分类已经饱和。

### 4.6 工作包2的核心原则

**Prompt 不是“咒语”，而是实验协议的一部分。** 只有把输入版本、Prompt 版本、输出字段、POC 约束、失败状态和统计口径固定下来，不同版本的差异才有解释力。

## 5. 工作包3：LLM 漏洞推理逻辑

### 5.1 三级推理框架

| 层级 | 检查内容 | 输出 | 防止的错误 |
| --- | --- | --- | --- |
| 第一层：语法检测 | 输入来源、变量传递、函数调用、字符串拼接、编码解码、存储读取、异常分支 | 片段 ID、局部行号、逐字引文、候选数据流 | 只看函数名就下结论 |
| 第二层：漏洞语义识别 | 输入是否可控、路径是否可达、防护是否适用、条件是否成立 | 必要条件、排除条件、证据缺口、候选/未检出/无法判定 | 把“有过滤函数”当成“有效防护” |
| 第三层：业务安全风险判定 | 身份、对象归属、状态、配置、部署环境、影响范围 | 确认/待验证/排除、适用范围、POC 成功条件 | 把一个条件下的结论推广到所有条件 |

三级框架的核心是**逐层降噪**：第一层只建立代码关系，第二层才判断漏洞语义，第三层才结合业务条件决定结论。

### 5.2 四类判定矩阵

| 类型 | 必要条件 | 排除条件（示例） | 实测确认要求 |
| --- | --- | --- | --- |
| SQL 注入 | 可控输入进入实际执行 SQL，能改变查询结构/语义 | 参数化绑定、严格白名单、与字符集/引用方式匹配的转义 | 正常行、真条件行、假条件空行/报错对照 |
| XSS | 输入到达浏览器可解释位置，缺少匹配上下文的编码 | 正确输出编码、安全文本写入、后续不解码 | 真实浏览器 DOM 执行标记，反射不算执行 |
| 命令注入 | 可控输入到达 shell/解释器，能改变命令语义 | 固定命令与参数、严格白名单、不经 shell 的解释执行 | `<pre>` 命令输出区出现独立标记，排除反射 |
| 权限越权 | 低权限主体可访问入口/控制对象，服务端缺少角色/对象/状态校验 | 服务端有效拒绝、对象绑定当前主体、状态约束 | 实际读取受保护数据，或更新后独立回查并恢复 |

### 5.3 证据等级与结论状态

- `high`：输入来源、关键操作、相关防护、业务路径的静态证据完整；
- `medium`：有关键候选，但存在条件/依赖缺口；
- `low`：只有线索，尚不足以建立完整路径。

证据等级不是漏洞概率，也不是风险严重程度。**静态证据再完整，没有同条件运行证据也只能是“待验证”。**

### 5.4 风险优先级 P1/P2

- P1：可能造成命令执行、敏感数据访问、跨用户修改或浏览器脚本执行，且有明确代码依据；
- P2：防护反例、边界案例、需要进一步梳理影响范围的候选；
- 待定：业务影响、入口可达性或关键上下文不足。

P1/P2 只用于安排核验顺序，不是 CVSS 评分，也不是最终严重程度。

### 5.5 代表性案例的设计作用

工作包3的 8 份案例文档覆盖：

- SQLI-001：直接拼接候选；
- SQL 参数化教学反例：有效防护长什么样（不计入 14 个父样本）；
- XSS-001：未编码输出候选；
- XSS-004：输出编码 + Token 的防护反例；
- CMD-001：直接拼接命令候选；
- CMD-004：四段数值校验的边界反例；
- AUTH-001 读取：high/impossible 拒绝非 admin；
- AUTH-001 更新：仅 impossible 拒绝非 admin。

案例的作用不是替代全量样本，而是给验证人员提供“成立前提、排除条件、成功现象、证据缺口”的模板。

### 6.4 判定证据类型

人工参考标签不是模型输出，也不是难度名称；它由执行人按下面的证据类型逐条判定，再由盲评复核。父标签只在主条件集合内聚合：任一必测路径确认阳性则父标签阳性；只有全部必测路径完成且有有效排除证据，才给父标签阴性；关键缺口未解决时保持“证据不足”。

| 类型 | 本次使用的确认证据 | 明确不使用的“伪证据” |
| --- | --- | --- |
| SQL 注入 | 正常行、真条件同值、假条件空行/报错；跨阶段数据库/登录回查 | 仅 SQL 报错、仅 HTTP 200、仅哈希 |
| XSS | 真实 Chrome 中 `window.__wp4xss`/DOM 标记；存储型写入-落库-读取-执行四段 | 仅响应中出现 payload、仅页面显示文本 |
| 命令注入 | `<pre>` 命令输出区出现独立标记，且页面其他位置无该标记 | 仅整个响应包含标记（可能是反射） |
| 权限越权 | 低权限读取受保护数据；更新后 MariaDB 独立回查并恢复 | 仅页面 200、仅 `result=ok`、仅前端显示成功 |

### 6.7 代表案例与原理

#### 案例一：SQLI-005 二阶注入（Less-24）

流程：

1. 正常注册 `wp4v`、登录、改密、再改回，证明正常功能可用；
2. 注册攻击者用户名 `wp4s' OR id=<victim_id>#`，数据库原样保存；
3. 登录时该值被写入 `$_SESSION['username']`；
4. 改密接口把 SESSION 值无转义拼进 `UPDATE users ... where username='$username'`；
5. 攻击者提交无关的 `current_password`，仍把 victim 口令改掉；
6. 独立登录回查：旧口令失败、新口令成功；攻击者口令未变；
7. 删除专用账号，不触碰预置管理员。

原理：**注册时的 SQL 转义不能覆盖后续的 SQL 拼接；数据库或 SESSION 中的值也不自动可信。** 这是“存储型/二阶注入”的典型数据流：写入时安全，读取后再次进入危险操作时不一定安全。

#### 案例二：AUTH-001 high 读取拒绝但更新仍可越权

普通用户 high：

- 页面 403；
- 读取 API 返回 `Access denied`；
- 更新 API 返回 `ok`，MariaDB 中 `wp4target.first_name` 从 `Wp4` 变为 `Wp4High`，随后恢复。

原理：**页面有检查，不等于独立 API 有检查；读取有检查，不等于更新有检查。** 这是“授权覆盖不一致”的典型问题。

#### 案例三：XSS-004 impossible 的 Token + 输出编码

- 同会话取得最新 token；
- 有效 token 请求：响应中出现 `&lt;svg`/`&quot;`，无原始 `<svg`；
- 浏览器无 `window.__wp4xss` 标记；
- 缺失 token：302，属于前置条件失败，**不能当作编码生效**。

原理：**Token 校验、输出编码、浏览器执行是三个不同层次。** 负例必须证明“有效请求到达目标代码且被正确编码”，而不是“没带 token 被拒绝”。

#### 案例四：CMD-003 high 的无空格管道绕过

- 源码黑名单替换 `'| '`（管道 + 空格）、`&`、`;` 等；
- 载荷 `127.0.0.1|printf WP4_CMD_003` 中 `|` 后没有空格，绕过替换；
- `<pre>` 中只出现 `WP4_CMD_003`，页面其他位置没有该标记。

原理：**过滤的是字符串，不是语义。** 只替换带空格的管道形式，不等于阻止管道操作符；命令注入必须看最终 shell 语义，而不是看黑名单名称。

### 6.8 统计口径与指标

分类指标只在以下条件同时满足时计算：

- 同一主条件集合；
- 完整 `parent` 输出（不是 partial）；
- 模型预测可确定为二分类；
- 人工标签最终确定；
- 预测与标签按相同 `sample_id + condition_key` 配对。

公式：

```text
Accuracy  = (TP + TN) / (TP + TN + FP + FN)
Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
F1        = 2TP / (2TP + FP + FN)
FPR       = FP / (FP + TN)
FDR       = FP / (TP + FP)
```

`无法判定`、`partial`、模型调用失败、未运行、标签证据不足**都不自动当阴性**；它们单独计数，并同时报告覆盖率。分母为 0 写“不适用”，没有实测写“待测”，指标必须同时显示分子、分母和样本清单。

本批 POC 指标：

| 指标 | 结果 | 说明 |
| --- | --- | --- |
| 父样本覆盖 | 14/14 | 每个父样本至少一条实测运行 |
| 运行记录 | 17/17 | AUTH 四条件分列 |
| 正例父样本触发 | 12/12 | 每个阳性父样本至少一条确认路径 |
| 条件级正例触发 | 14/14 | 含 AUTH low/medium/high |
| 负例回归 | 2/2 | XSS-004、CMD-004 在限定范围未触发 |
| AUTH 条件矩阵 | 4/4 | low/medium/high/impossible |
| 证据完整率 | 17/17 | request/response/observation/restore 齐全 |
| 模型 POC 生成覆盖 | 12/12 | 正例模型输出含完整 POC 代码，不代表可运行 |
| 模型 POC 原稿完成率 | 待测 | 模型 POC 未直接执行 |
| 模型 POC 端到端成功 | 待测 | 未测，不能与人工适配 POC 混算 |

#### 6.9.4 第二轮修正：final-wp4-v1 → final-wp4-v2

CR-008 针对两个根因：

1. `vulnerability_type` 必须精确等于 `audit_scope`，不能用“XSS（反射型）”“SQL注入（二阶）”等子类型；
2. `success_criteria`/`expected_observation` 必须是字符串；负例 `exclusion_evidence` 不得少于基线。

## 8. 实验原理：为什么这样设计

### 8.1 固定提交与完整源码

审计片段不能直接当页面运行；同一行代码在不同版本、不同配置下可能行为不同。固定提交 + 完整源码 + 部署副本哈希，保证“模型看到的代码”和“实际运行的代码”是同一版本。

### 8.2 标准化与行号映射

模型需要的是数据流，不是页面装饰。标准化减少噪声，但必须保留输入、过滤、查询、执行、输出、错误处理；局部行号 + 逐字引文 + 行号映射，使每个引用都能回到原始文件。

### 8.3 四段式 Prompt 与统一协议

四段式把“角色、任务、标准、输出”分开，统一协议把“预测、结论、POC、限制”变成可机械检查的字段。这样不同版本才能比较，失败也能分类，而不是只看“答得像不像”。

### 8.4 三级推理与判定矩阵

语法层只建立关系，语义层才判断漏洞，业务层才结合身份/对象/配置。判定矩阵把“必要条件、排除条件、证据要求”写死，防止：

- 看到 `mysql_query` 就报 SQL 注入；
- 看到 `str_replace` 就判安全；
- 看到 `is_numeric` 就判命令注入不可能；
- 看到页面 403 就判 API 也安全。

### 8.5 静态预测与实测确认分离

模型可以说“存在候选”，但不能说“确认”；确认必须引用同路径、同角色、同配置、同版本的运行证据。HTTP 200、反射、`result=ok`、脚本能跑，都不够。这个分离是本实验最重要的方法论。

### 8.6 父样本聚合与条件键

同一父样本可以有多个路径、多个配置、多个对象。统计单位是父样本，条件单位是 `condition_key`。AUTH-001 的 low 读取、high 读取、high 更新、impossible 更新分别记录；父标签只在“主条件集合”内聚合，条件级阴性不推翻父样本阳性。

### 8.7 负例与证据不足

负例不是“没跑出结果”，而是“在限定路径/条件下，有完整代码路径、有效防护和运行对照”。证据不足、环境失败、认证失败、Token 失败都不能自动算阴性。这样才能避免通过排除难样本抬高指标。

### 8.8 证据驱动优化

优化不是“改 Prompt 试试”，而是：

```text
实测问题 → change request → 新版本 → 同输入/同模型/同条件复测
→ 配对比较 → 报告提升/退步/不变/未知 → 保留旧版本
```

本实验的 v1 提升了 POC 契约但造成格式退步和负例证据下降；v2 再修正格式和负例。这个过程本身比“最后看起来都很好”更有展示价值，因为它说明实验能够发现并承认副作用。

## 9. 效度、限制与伦理

### 9.1 内部效度

**做得好的地方：**

- 固定提交、固定输入、固定 Prompt、固定模型家族、固定本地环境；
- 每类漏洞有明确的成功标准和反例；
- 17 条运行有请求、响应、观察、恢复和哈希；
- AUTH 按四个条件分列，避免条件混淆；
- 优化批次同输入、同模型、同条件，配对比较；
- 最终状态校验通过，证据可复现。

**仍需注意：**

- 模型批次是子代理辅助，不是正式 API；快照/温度/用量未知；
- 多包样本一次性提供，未严格逐包追加；
- 模型与验证执行者同属一个模型家族，存在记忆偏差和确认偏差；
- 盲评是模型辅助，不是人工签字；
- 严格格式通过只证明可机械核验的字段，不证明语义正确。

### 9.2 外部效度

- 样本只有 14 个，且来自两个公开教学靶场；
- 同源难度版本高度相关，不能当作 14 个独立真实业务样本；
- 代码直接出现在 Prompt 中，模型可能识别公开靶场；
- 分类 14/14 不能外推为真实业务代码的准确率；
- 负例只覆盖已测路径和配置，不能证明整个应用安全。

### 9.3 构念效度

- `Accuracy/Precision/Recall/F1` 衡量的是“与人工标签的一致率”，不是“模型通用审计能力”；
- `high/medium/low` 是证据等级，不是概率/严重程度；
- `P1/P2` 是核验顺序，不是 CVSS；
- 严格静态协议是格式/引用检查，不是漏洞判断质量；
- POC 契约评分是关键词/完整性启发式，不是人工质量评分；
- 负例排除证据条数是机械计数，不等于论证质量。

### 9.4 伦理与安全

- 只在本地授权靶场测试，不访问公网目标；
- 只使用专用测试账号/对象/留言，执行后删除或恢复；
- SQL 不枚举/导出数据；XSS 只用无害 DOM 标记；命令注入只回显固定标记；越权写操作有原值、回查和恢复；
- 证据不保存 Cookie、口令、Token；
- 报告明确区分“学习实验”与“真实业务安全评估”。

## 10. 结论与后续工作

### 10.1 结论

1. **流程闭环已经形成**：从固定源码到标准化输入、Prompt、推理规则、本地实测、证据、模型对照、优化复测、清理和最终校验，每一环都有产物。
2. **实测结论明确**：12 个父样本确认目标漏洞，2 个负例在限定范围未触发；AUTH-001 的读取/更新保护不一致，SQLI-005 的二阶注入链成立。
3. **模型分类饱和**：三版 Prompt 和多个批次均为 14/14；真正有区分度的是格式、POC 证据和负例论证，而不是准确率。
4. **优化有真实副作用**：v1 提升 POC 契约但造成格式退步和负例证据下降；v2 修正到 14/14 并恢复负例证据。这个过程说明实验能够发现、记录和修正问题，而不是只报好消息。
5. **证据可复核**：17/17 证据完整、17/17 盲评一致、33/33 源码哈希一致、最终状态校验通过；但仍是子代理辅助，不是人工签字或正式 API。

### 答辩口径（常见问题）

**Q1：为什么分类都是 14/14？是不是数据太简单？**

**Q3：严格协议为什么有失败？**

**Q4：怎么证明不是“自己说自己对”？**  
A：三类证据：真实浏览器执行、MariaDB/登录独立回查、17 条盲评；同时保留失败、退步和限制。盲评是子代理，不是人工签字，这一点报告里明确写了。

## 结语

这项实验最重要的产出，不是“14/14”这个数字，而是一套**能把模型判断落回证据、把证据落回代码、把优化落回版本**的方法。它允许我们说清楚：

- 哪些结论是实测确认的；
- 哪些只是静态候选；
- 哪些负例是真正有排除证据的；
- 哪些提升伴随着退步；
- 哪些结果不能外推。

对展示而言，建议把“证据链”和“优化副作用”作为主线，而不是只展示准确率。这样既能体现工程的完整性，也能体现实验的诚实性和可复现性。
